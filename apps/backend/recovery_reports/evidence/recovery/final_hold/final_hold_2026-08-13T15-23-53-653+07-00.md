## Observability improvement proposal (read-only)

The current request logging architecture only attaches a correlation ID and records method/url/IP/User-Agent via the logger middleware, but it does not retain the request body for transaction creation requests. The audit interceptor records metadata for routes marked with @Audit, and the transaction create route is not covered by that path. This is the critical observability gap for incident reconstruction.

Read-only proposal:

1. correlation/request ID propagation
   - require x-correlation-id propagation from ingress to application to downstream services
   - preserve across gateway, proxy, app, and audit logs
2. safe transaction request metadata logging
   - record method, path, route, tenant/account IDs, request timestamp, actor info, and redacted field summary without logging raw secrets or full PII
3. amount_cents observability with privacy controls
   - capture a redacted amount summary (e.g., cents, currency, and source) only in structured logs with retention and access controls
4. structured request/response audit records
   - emit a dedicated audit event for create-transaction requests with request metadata, result status, correlation ID, and invariant checks
5. centralized log retention
   - retain request metadata, gateway records, and audit trails in a centralized export path with immutable retention windows
6. gateway/proxy correlation
   - map ingress, proxy, and app IDs to one transaction trace so exact client submissions can be correlated to DB writes
7. anomaly detection for ×100/÷100
   - alert when transaction amounts are exact multiples of 100 in suspicious patterns and when they differ from the submitted value in a way that indicates scaling errors
8. ledger reconciliation
   - maintain a deterministic reconciliation log showing pre/post ledger totals and transaction deltas to improve incident review
9. immutable audit trail
   - keep immutable request and decision artifacts with checksums and hash manifests for audit and incident review
10. incident recovery evidence requirements
   - treat request evidence and human authorization as explicit preconditions for any production recovery path

This proposal is documentation-only and intentionally does not change application behavior in this phase.
